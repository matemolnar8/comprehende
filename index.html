Comprehende?

Stops comprehension debt from growing
while agents write the code.

The agent writes the how. Comprehende gives you the why and the what.

Agents write faster than we can read

  • A pull request lists files in alphabetical order. That is how git stores them, not how you read a change.
  • The tests pass and the code looks clean, so we approve it unread. That is cognitive surrender.
  • Each unread change adds comprehension debt. Nobody chose it and nobody can see it.
  • The debt comes due in an incident or a long debug session.

From surrender back to offloading

surrender→offloading

Surrender

  • The agent decides what the change is and you take its word.
  • You have no view of your own to compare with the code.
  • The pull request is approved and the understanding is gone.

Offloading

  • The agent still writes the how. That part stays offloaded.
  • Comprehende gives you the why and the what for each group of hunks.
  • You check that view against the live diff. The understanding stays with you.

A review assistant for any git diff

A skill and a small CLI. Your coding agent groups the diff by review concern and writes a why and a what for each group. A fixed local web UI shows the groups next to the real diff from git.

group · 3 hunks

Token refresh. Why: issue #42 asks for silent re-login. What: a new helper and two call sites.

group · 1 hunk

Retry on 401. Why: enables the group above. Look for: the retry has no cap.

mechanical · 14 files

Renamed test fixtures. Same change in every file. Safe to skim.

Install and use

# once, in any repo
npx skills add matemolnar8/comprehende

# in your coding agent, name what to review
/comprehende PR 154
/comprehende the changes from the last turn
/comprehende feature/auth against main

The agent writes review.json and prints a local URL. Needs Node.js 24+ and git. The diff never leaves your machine.

What you get in the UI

  • Groups by review concern. Each group has a why, a what, and a size that means review burden, not file count.
  • Parts. Work that could have been its own pull request gets its own story and a suggested reading order.
  • Look for. Claims the diff does not make obvious, with the source cited. No pass or fail.
  • Sources. The tickets, pull request comments, commits, and agent transcripts the agent read, each with a gist.
  • Full files and git blame. One click from any hunk. The diff always comes from live git.
  • Refresh. New commits keep the old groups. The What changed page shows the delta.
  • Mechanical groups. Renames and generated output, marked so you know what to skip.
  • Keyboard. j k move, v marks viewed, o opens the overview. Every view has a URL you can share.

Goals

  • Accuracy. Live git wins. The review file holds interpretation only and never stores diff text.
  • Coverage. Every hunk is in a group, or validate fails.
  • Fixed UI. The same UI every time. Only the data changes.
  • Local. No hosted service and no account.
  • Plain words. Simplified Technical English in the UI and in the generated text.

Non-goals

  • Review for you. It gives you a view to hold against the diff. You still read the diff.
  • Judge. No approve or reject and no score. Look for items are claims to check, not verdicts.
  • Replace git. No stored patches and no second source of truth.
  • Know your forge. GitHub, GitLab, Bitbucket, and Jira live in the skill, not in the tool. The core is plain git.
  • Generate UI. The model never draws a screen.

How it works

  1. The CLI indexes base...head and writes a skeleton. One entry per changed file, hunk refs, stub prose.
  2. The agent fills the interpretation. Title, groups, why, what, look for, sources. It never invents a hunk ref.
  3. Validate, then serve or export. Every ref must resolve in live git. The UI reads the diff from git when you open it.
